# انتشار خودکار هوشمند پارسی با PHP و Cron

این سایت HTML/CSS/JS ایستا است و Build لازم ندارد. هاست هر ۵ دقیقه شناسهٔ Commit شاخهٔ main را از GitHub می‌پرسد؛ فقط برای Commit جدید آرشیو دریافت می‌شود. حالت آزمایشی نتیجهٔ معتبر را نگه می‌دارد و برای همان Commit دوباره آرشیو دانلود نمی‌کند. اگر پروژه در آینده به Build نیاز پیدا کرد، باید خروجی آمادهٔ Build در GitHub Actions تولید و روش دریافت خروجی جداگانه تنظیم شود؛ کد فعلی برای انتشار سورس یک پروژهٔ Buildدار مناسب نیست.

## مسیرها و نصب اولیه

همهٔ فایل‌های بستهٔ نصب را **خارج از public_html** در این پوشه قرار دهید:

`/home/pendariu/domains/hoosh-parsi.ir/deploy-private/`

- `deploy.php`: اجراکنندهٔ اصلی، فقط CLI؛ در وب قابل اجرا نیست.
- `doctor.php`: بررسی نسخهٔ PHP، افزونه‌ها، مسیرها و دسترسی GitHub؛ بدون تغییر فایل‌های سایت.
- `config.php`: نسخه‌ای از config.example.php با تنظیمات این دامنه؛ در بسته بدون توکن است.
- `README.fa.md`: همین راهنما؛ لازم نیست در وب نمایش داده شود.
- `github-token.txt`: فقط در صورت نیاز به مخزن خصوصی، روی خود هاست ایجاد شود؛ در بسته یا GitHub نیست.
- پوشه‌های `runtime/` و `backups/` خودکار همان‌جا ساخته می‌شوند؛ هرگز آن‌ها را به public_html منتقل نکنید.

مسیر سایت از فایل‌منیجر این حساب تأیید شده است:

`/home/pendariu/domains/hoosh-parsi.ir/public_html`

پوشهٔ خصوصی مجوز 0700 و فایل توکن/تنظیمات 0600 داشته باشند. خود اجراکننده نیز مجوزها را محدود می‌کند. فایل‌های عمومی با 0644 و پوشه‌های جدید با 0755 ساخته می‌شوند. روی پوشهٔ خصوصی هیچ دامنه، Alias یا Document Root تعریف نکنید. هیچ فایل محرمانه‌ای نباید وارد GitHub شود.

## توکن برای مخزن خصوصی

مخزن در زمان نصب عمومی است؛ بدون توکن هم کار می‌کند. اگر خصوصی شد:

1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
2. Resource owner: seopersiann؛ Repository access: Only select repositories → فقط hoosh-parsi.
3. Repository permissions: **Contents: Read-only**؛ Metadata: Read-only خودکار. هیچ مجوز Write، Administration، Workflows یا Actions لازم نیست.
4. تاریخ انقضای مشخص انتخاب کنید و برای تمدید آن یادآوری بگذارید. پس از انقضا انتشار متوقف می‌شود و سایت قبلی باقی می‌ماند.
5. روی هاست، فایل `deploy-private/github-token.txt` بسازید و فقط خود توکن را در یک خط وارد کنید؛ مجوز 0600. توکن را در چت، کد مخزن، دستور Cron، URL یا گزارش وارد نکنید.

توکن فقط برای api.github.com ارسال می‌شود؛ هنگام انتقال دانلود به codeload.github.com، هدر Authorization ارسال نمی‌شود. اعتبار TLS بررسی می‌شود.

مستندات رسمی مجوز دریافت آرشیو: https://docs.github.com/en/rest/repos/contents#download-a-repository-archive-zip

## بررسی PHP و اجرای آزمایشی

در Netafraz اجرای /bin/sh در Cron مجاز نبود؛ باید فرمان PHP مستقیم استفاده شود. مسیر زیر از نمونهٔ مجاز پنل گرفته شده و با گزارش doctor تأیید می‌شود:

```
/usr/local/bin/php /home/pendariu/domains/hoosh-parsi.ir/deploy-private/doctor.php > /home/pendariu/domains/hoosh-parsi.ir/deploy-private/doctor-report.json 2>&1
```

برای این فرمان موقتاً Minute=`*/5` و چهار فیلد دیگر `*` بگذارید. بعد از ایجاد گزارش، همان Cron را ویرایش کنید، نه اینکه چند Cron هم‌زمان بسازید. PHP CLI حداقل 8.1، cURL، ZipArchive، JSON، flock و امکان نوشتن روی پوشهٔ خصوصی و سایت لازم‌اند. در صورت قدیمی‌بودن PHP، مسیر PHP CLI نسخهٔ 8.1 یا بالاتر را از پشتیبانی هاست بگیرید؛ تنظیم نسخهٔ PHP وب لزوماً نسخهٔ CLI را تغییر نمی‌دهد. گزارش doctor وضعیت واقعی را مشخص می‌کند.

config.php باید ابتدا `'mode' => 'dry-run'` داشته باشد. فرمان Cron اصلی:

```
/usr/local/bin/php /home/pendariu/domains/hoosh-parsi.ir/deploy-private/deploy.php > /home/pendariu/domains/hoosh-parsi.ir/deploy-private/cron-last.log 2>&1
```

زمان‌بندی: **`*/5 * * * *`**. در فرم DirectAdmin فقط `*/5` در دقیقه، `*` در ساعت، روز ماه، ماه، روز هفته؛ فرمان را در کادر جداگانه قرار دهید.

بعد از اولین اجرا، `runtime/deploy.log` باید پیام `DRY_RUN_OK` نشان دهد و `runtime/dry-run-ok.json` ایجاد شود. آرشیو و فایل‌ها در پوشهٔ موقت بررسی شده‌اند و هیچ فایل سایت جایگزین یا حذف نشده است. در صورت خطا، روی dry-run بمانید. اگر main قبل از اولین انتشار تغییر کرد، یک dry-run موفق برای Commit جدید لازم است.

## فعال‌سازی

فقط بعد از DRY_RUN_OK، در config.php مقدار mode را به `live` تغییر دهید. فرمان و زمان‌بندی Cron همان قبلی می‌مانند. اجرای بعدی بکاپ می‌گیرد و نسخهٔ معتبر را منتشر می‌کند. `PUBLISHED` همراه Commit و شناسهٔ بکاپ در گزارش ثبت می‌شود. اگر Commit تغییری نکرده باشد، پیام `UNCHANGED` ثبت می‌شود و دانلودی انجام نمی‌شود.

## مسیرهای مجاز و حفاظت از فایل‌ها

قواعد مسیر هستند، نه فهرست دستی عکس‌ها و صفحات:

- فایل‌های HTML/CSS/JS/XML در روت، و robots.txt.
- HTML داخل پوشه‌های صفحات با هر نام جدید، به‌جز پوشه‌های ممنوع.
- پوشهٔ assets و زیرپوشه‌ها با پسوندهای ایستای مجاز در config.example.php؛ عکس، فونت، JSON و MP4 جدید خودکار اضافه می‌شوند.
- PHP، فایل‌های مخفی، .htaccess، .user.ini، .env، تنظیمات سرور، deploy، scripts، tests، deliverables و پوشه‌های وابستگی منتشر نمی‌شوند.
- uploads، media، storage، wp-content، assets/uploads و assets/user-uploads محافظت می‌شوند. اگر آپلود کاربران در مسیر دیگری است، **قبل از live** آن مسیر را به protected_paths اضافه و دوباره dry-run کنید.
- فایل‌های نامرتبط موجود روی هاست حذف نمی‌شوند. در اولین انتشار فقط فایل‌هایی که در محدودهٔ مجاز و خود مخزن هستند به مالکیت انتشار وارد می‌شوند؛ بکاپ نسخهٔ فعلی آن‌ها گرفته می‌شود. بعداً فقط فایل‌های ثبت‌شده در state.json قابل حذف به‌عنوان فایل منسوخ پروژه‌اند.
- اگر فایل مدیریت‌شده روی هاست دستی تغییر کند، انتشار متوقف می‌شود تا تغییر دستی از بین نرود. تغییر را به مخزن منتقل یا با بکاپ/نسخهٔ قبلی تطبیق دهید؛ state.json را برای عبور از خطا حذف نکنید.
- Symlink در مقصد و فایل‌های آرشیو مجاز نیست. ZIP مستقیماً در public_html استخراج نمی‌شود. اندازه، مسیر، تعداد فایل‌ها و Git blob SHA-1 هر فایل با درخت همان Commit بررسی می‌شود و هنگام نصب SHA-256 نیز بررسی می‌شود.

## بکاپ، شکست اجرا و بازگشت

قبل از هر انتشار، از همهٔ فایل‌های پروژه که قرار است تغییر کنند، از جمله فایل‌های حذف‌شدنی، در backups/شناسه/files بکاپ گرفته می‌شود. manifest.json وجود قبلی، مجوزها و هش‌ها را ثبت می‌کند. پوشهٔ بکاپ و وضعیت انتشار خارج از وب هستند.

هر فایل با rename اتمیک جایگزین می‌شود؛ فایل‌های استاتیک قبل از HTML و index.html در آخر نصب می‌شوند. **کل درخت سایت یک‌باره اتمیک نیست**؛ هنگام انتشار چندثانیه‌ای ممکن است بعضی درخواست‌ها ترکیبی از فایل‌های دو نسخه را ببینند. به‌دلیل اشتراکی‌بودن public_html و لزوم حفظ فایل‌های هاست، روت با Symlink تعویض نمی‌شود.

شکست حین انتشار باعث بازیابی خودکار می‌شود. قطع کامل فرایند هم journal.json را باقی می‌گذارد؛ Cron بعدی ابتدا بازیابی می‌کند و انتشار را PAUSED می‌گذارد. فایل‌های نامرتبط و آپلود کاربران در بازگشت نیز حفظ می‌شوند. اجرای هم‌زمان با flock متوقف می‌شود.

برای بازگشت دستی، **موقتاً همان Cron** را به این فرمان تغییر دهید:

```
/usr/local/bin/php /home/pendariu/domains/hoosh-parsi.ir/deploy-private/deploy.php --rollback > /home/pendariu/domains/hoosh-parsi.ir/deploy-private/cron-last.log 2>&1
```

بعد از مشاهدهٔ `ROLLED_BACK` فرمان Cron را به حالت عادی برگردانید. انتشار خودکار Paused باقی می‌ماند و rollback در اجراهای بعدی تکرار نمی‌شود. اگر فایل پروژه بعد از آخرین انتشار دستی تغییر کرده باشد، بازگشت دستی برای حفظ آن تغییر متوقف می‌شود؛ از بکاپ خصوصی با بررسی دستی استفاده کنید.

پس از اصلاح مشکل برای ادامه، یک بار همان Cron را با `--resume` اجرا کنید، سپس به فرمان عادی برگردانید. این کار تنها Pause را برمی‌دارد؛ اجرای عادی بعدی دوباره main را بررسی می‌کند. در صورت نیاز قبل از resume، mode را dry-run کنید. برای وضعیت، گزینهٔ `--status` موجود است.

برای بازیابی کاملاً دستی، ابتدا Cron این پروژه را متوقف کنید، فایل‌های پوشهٔ بکاپ files را مطابق manifest.json در public_html کپی کنید؛ فایل‌هایی که existed=false دارند در نسخهٔ قبلی وجود نداشتند. journal و state را بدون بررسی سازگار نکنید. نسخهٔ بکاپ را تا پایان بررسی نگه دارید.

## گزارش‌ها و محدودیت‌ها

- runtime/deploy.log: تاریخچهٔ نتیجه، با چرخش پس از ۵ مگابایت؛ نسخهٔ قبلی deploy.log.1.
- cron-last.log: خروجی آخرین Cron و خطاهای اولیه/نسخهٔ PHP.
- doctor-report.json: نتیجهٔ بررسی هاست.
- runtime/state.json: Commit منتشرشده و فهرست فایل‌های متعلق به پروژه.
- runtime/candidate.json و stage-* : آخرین نسخهٔ اعتبارسنجی‌شده.
- runtime/journal.json: تراکنش قطع‌شده؛ حذفش نکنید.
- runtime/paused.json: توقف ایمن بعد از بازیابی.

HTTP 401/403: توکن، انقضا یا محدودیت درخواست. 404: آدرس مخزن/مجوز دسترسی. خطای cURL: اتصال خروجی هاست به GitHub یا گواهی TLS. هر خطای دانلود/هش، سایت قبلی را حفظ می‌کند. اگر هاست خروجی HTTPS به GitHub را مسدود کند، باید پشتیبانی هاست آن را مجاز کند؛ نیازی به IP ثابت اتصال ورودی نیست.

بکاپ‌ها خودکار حذف نمی‌شوند تا نسخهٔ قابل بازگشت از دست نرود. مصرف فضای backups و stageهای قدیمی را دوره‌ای بررسی کنید. فقط در زمان توقف Cron، بکاپ‌های قدیمی غیرمرتبط با state.backup و journal.backup و stageهای غیرمرتبط با candidate.stage را پس از گرفتن نسخهٔ خارج از هاست حذف کنید. هیچ فایل روی public_html برای پاک‌سازی فضا به‌طور عمومی حذف نمی‌شود.

اسکریپت انتشار خودش را از مخزن خودکار جایگزین نمی‌کند؛ به‌روزرسانی ابزار انتشار باید پس از بررسی، جداگانه روی پوشهٔ خصوصی نصب شود. عمومی/خصوصی‌بودن مخزن با این اسکریپت تغییر نمی‌کند. توکن فقط‌خواندنی هم امکان تغییر مخزن ندارد.

آزمون محلی: `php tests/test_directadmin_deploy.php`؛ آزمون‌ها دانلود ناقص، هش غلط، مسیر نامجاز، تغییر دستی، حفاظت آپلود، حذف فایل منسوخ پروژه، بازیابی پس از قطع، قفل و بازگشت را پوشش می‌دهند.

## اصلاح مجوز پوشه‌های تازه (نسخهٔ ۷ نوامبر ۲۰۲۶)

در نسخهٔ اولیه، umask خصوصی 0077 روی ساخت پوشهٔ عمومی نیز اثر می‌گذاشت؛ در نتیجه پوشهٔ صفحهٔ جدید با 0700 ساخته می‌شد و وب‌سرور می‌توانست خطای 403 بدهد، هرچند فایل و هش آن درست بودند. نسخهٔ اصلاح‌شده فقط هنگام ساخت پوشهٔ عمومی، umask را موقتاً 0022 می‌کند و سپس آن را به حالت خصوصی برمی‌گرداند. آزمون محلی، 0755 بودن مسیر عمومی و 0700 ماندن runtime را بررسی می‌کند.

اسکریپت‌ها خودکار از مخزن روی پوشهٔ خصوصی هاست نصب نمی‌شوند. برای نصب اصلاح، فقط deploy.php جدید را در /home/pendariu/domains/hoosh-parsi.ir/deploy-private/deploy.php جایگزین کنید. config.php، توکن، runtime و backups را دست‌نخورده نگه دارید.

پوشه‌ای که قبلاً با مجوز محدود ساخته شده است، با این تغییر به‌تنهایی تعمیر نمی‌شود. در File Manager، مجوز پوشهٔ /home/pendariu/domains/hoosh-parsi.ir/public_html/article-cart-abandonment را یک بار به 0755 تغییر دهید؛ فایل index.html باید 0644 باشد. عملیات بازگشتی روی همهٔ پوشه‌های حساب انجام ندهید و مجوز پوشهٔ خصوصی انتشار را تغییر ندهید.
